# ADR-005: Error Handling & Process Termination Hierarchy

## Status
Accepted

## Date
2026-10-21

## Context
In the original codebase, error handling was inconsistent:
- Some failures threw generic `std::runtime_error`.
- Some out-of-bounds reads caused undefined behavior or assertion failures in Debug builds while silently continuing in Release builds.
- Memory allocation failures inside `sodium_malloc()` resulted in immediate `std::abort()` without diagnostic logging.
- Native host message loop could crash on malformed JSON or unhandled exceptions, breaking the browser pipe without returning a structured JSON error response.

## Decision
Establish a strict three-tier error handling and termination hierarchy:

### Tier 1: Catastrophic Invariant Violations (Fail Fast via `std::abort()`)
- **Scenarios**: `sodium_malloc()` failure when allocating internal runtime secrets (e.g. derived vault master key, session crypto state), memory guard canary corruption, internal cryptographic assertion failure.
- **Action**: Immediate termination via `std::abort()` or OS hardware trap.
- **Rationale**: Never attempt error recovery or fallback to unhardened heap memory when secure memory or cryptography invariants fail for core application state.

### Tier 2: Domain, Resource & IO Errors (Typed Exceptions)
- **Scenarios**: Corrupted vault file header, MAC authentication failure (wrong master password), file read/write permission errors, invalid CLI input, untrusted file structural violations (truncated payload, invalid entry count > (size-pos)/66 or > 1,000,000, length exceeding remaining bytes), decrypted payload size exceeding `kMaxSecureBufferBytes` (64 MiB), or `sodium_malloc()` exhaustion (`try_allocate` returning NULL) while allocating untrusted entry payloads during deserialization.
- **Action**: Use typed exception classes derived from `std::runtime_error`:
  - `pwledger::VaultCorruptException`: thrown on malformed headers, magic mismatch, unsupported version, truncated fields, or invalid structural counts.
  - `pwledger::VaultResourceException`: thrown when payload size exceeds safe limits or secure memory allocation fails during untrusted deserialization.
  - `pwledger::AuthenticationFailedException`: thrown on decryption MAC failure.
  - `pwledger::VaultIoException`: thrown on filesystem I/O errors.
- **Policy Decision**: The target standard is C++20 (`std::expected` is C++23). We standardize strictly on typed domain exceptions and do not mix result types and exceptions. Domain, cryptographic authentication, and filesystem errors are signaled via typed exceptions and caught cleanly at top-level command loops (`apps/cli/CommandLoop.cc` and `apps/native_host/MessageLoop.cc`).
- **Resource Exhaustion Clarification**: `std::abort()` applies strictly to internal runtime invariant failures. When handling untrusted input (such as ciphertext buffer sizing or deserializing entries), out-of-bounds lengths or allocation failures result in non-aborting typed exceptions (`VaultCorruptException` / `VaultResourceException`), preventing an attacker-controlled vault file from crashing the process.

### Tier 3: Native Messaging Boundary (Never Throw across Stdio Pipe)
- **Scenarios**: Any exception or parse failure during processing of a browser request.
- **Action**: The outer message loop catches all `std::exception` and unknown exceptions, formats a structured JSON error response `{"error": "...", "id": ...}`, and writes it to stdout before continuing the loop.
- **Rationale**: An uncaught exception causes the host to terminate abruptly, leading Chrome/Firefox to display an unhelpful "Native host has exited" error.

## Consequences
- Robust error recovery in CLI and native host.
- Zero chance of fallback to insecure memory on catastrophic allocation failures.
