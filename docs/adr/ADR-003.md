# ADR-003: Fail-Closed Native Host Extension Origin Validation

## Status
Accepted

## Date
2026-10-21

## Context
`pwledger-host` is invoked by Chrome and Firefox via the OS Native Messaging protocol over stdio. In the original implementation, `main.cc` defined `int main()` without command-line parameters, completely ignoring `argc` and `argv`. Furthermore, while `Config.h` declared `IntegrationConfig::allowed_extensions`, the allow-list was never consulted.

This left the host open to connections from any browser extension or unprivileged local process capable of spawning `pwledger-host`.

## Decision
1. **Multi-Browser Argument Parsing**:
   - `main(int argc, char* argv[])` will scan all command-line arguments passed by the calling browser.
   - **Chrome / Chromium**: Browser passes `argv[1]` = `chrome-extension://<extension_id>/`. On Windows, Chrome also passes `--parent-window=<HWND>`. The parser must filter out `--parent-window=...` and extract the normalized extension ID from `chrome-extension://`.
   - **Firefox**: Browser passes `argv[1]` = absolute path to the native messaging manifest, and `argv[2]` = add-on ID (from `manifest.json`). The parser must recognize the manifest path and extract the add-on ID from `argv[2]`.
   - Normalize IDs to lowercase and strip leading/trailing slashes.
2. **Fail-Closed Policy**:
   - If `allowed_extensions` is empty, or if the calling extension ID does not match any entry in `allowed_extensions`, the host must **fail closed**:
     - Print an error diagnostic to `std::cerr` detailing the rejected origin and instructions on how to configure `allowed_extensions`.
     - Immediately terminate the process with exit code `1` before reading any input from `stdin`.
3. **Installer Updates**:
   - `setup/setup.sh` and `setup/setup.ps1` will be updated to automatically populate `allowed_extensions` with the installed extension ID.
4. **Defense-in-Depth Boundary Statement**:
   - Because any unprivileged process executing under the same user desktop session can spawn `pwledger-host` with arbitrary spoofed `argv` parameters, `argv` validation constitutes defense in depth against unauthorized browser extensions, not a cryptographic security boundary against malicious local code.

## Doubt-Driven Scrutiny
- **CLAIM**: Parsing `argv` and matching against `allowed_extensions` prevents unauthorized extension access.
- **EXTRACT**:
  ```cpp
  std::string origin = detect_extension_origin(argc, argv);
  if (!is_allowed_extension(cfg, origin)) {
      std::cerr << "[ERROR] Unauthorized extension: " << origin << "\n";
      return 1;
  }
  ```
- **DOUBT**: If a user runs `pwledger-host` manually from the terminal for debugging, or if a browser extension is reinstalled with a new temporary ID during development, will fail-closed prevent legitimate troubleshooting?
- **RECONCILE**: A password manager must prioritize credential confidentiality over ease of ad-hoc unauthenticated invocation. Failing closed when unconfigured prevents silent exposure. Because `argv` is completely attacker-controlled by local processes, any command-line bypass flag (such as `--debug-extension-id`) would completely defeat the fail-closed defense. Debug IDs must be configured solely via the configuration file (`pwledger.json`). If `allowed_extensions` is empty or unmatched, the host exits with code 1 before reading anything from `stdin`.
- **STOP**: Confirmed accepted. Failing closed is mandatory for security.

## Consequences
- Rogue browser extensions cannot communicate with `pwledger-host`.
- Unconfigured installations fail loudly with clear diagnostic instructions rather than silently serving credentials.
- `setup/` scripts are tightly coupled to the allow-list configuration.
