# ADR-002: Secret Payload-Length & V1 Compatibility Model

## Status
Accepted

## Date
2026-10-21

## Context
In the original codebase, `Secret` allocated a fixed capacity (e.g. 64 bytes via `sodium_malloc`), but neither `Secret` nor `SecretEntry` recorded the actual number of valid bytes in the secret payload. Consequently, `VaultSerializer::serialize()` used `::strnlen(buf.data(), buf.size())` to determine the length to write into the vault file.

This created two critical flaws:
1. **Truncation of Binary Secrets**: Passwords or cryptographic keys containing `0x00` were silently truncated at the first null byte.
2. **Buffer Over-Read**: Secrets without a trailing null byte read uninitialized canary bytes (`0xdb`) up to buffer capacity.

We need to fix this without changing the on-disk binary format, because existing user vaults must remain readable.

## Decision
1. **Explicit Payload Length in `Secret`**:
   - `Secret` will store `payload_len_` explicitly alongside allocated `capacity_`.
   - Accessors `with_read_access()` and `with_write_access()` will expose `std::span` bounded by `payload_len_` (or requested length), preventing reads beyond valid payload boundaries.
2. **100% V1 Byte-Level Compatibility**:
   - The V1 vault binary format already records `secret_len` as a 32-bit unsigned integer preceding the secret bytes:
     `[secret_len: 4B][secret_bytes: secret_len B]`
   - Serializing `payload_len_` bytes requires **no change to the V1 format structure**.
   - No format version bump is performed.
3. **Documented Legacy Limitation**:
   - Older vaults created with the original code that contained passwords with embedded null bytes were already truncated when written to disk by the original code. Those truncated bytes cannot be recovered. Deserializing such vaults will read the truncated secret as stored on disk.
4. **Compatibility Fixture**:
   - A fixture vault file produced by the original code (`tests/fixtures/v1_original_vault.pwl`) will be stored in git and tested in every CI run to guarantee that refactored code can open original vaults.

## Doubt-Driven Scrutiny
- **CLAIM**: Writing exact secret length is completely backward-compatible with V1 format and will not break any existing vault.
- **EXTRACT**:
  In `VaultSerializer.cc:113`:
  ```cpp
  std::uint32_t secret_len = read_u32(data, pos);
  Secret secret = Secret::allocate(secret_len);
  secret.with_write_access([&](std::span<char> buf) {
    std::memcpy(buf.data(), data.data() + pos, secret_len);
  });
  ```
- **DOUBT**: Did the original deserializer expect a null terminator byte inside `secret_bytes`? If an exact length is written without a trailing null byte, will existing CLI display or clipboard operations crash when treating it as a C-string?
- **RECONCILE**: The original deserializer allocates `Secret::allocate(secret_len)` and reads exactly `secret_len` bytes into the buffer. The format does not reserve a byte for a trailing null. However, CLI display and clipboard code in the original implementation relied on `std::string(buf.data(), len)` or `strnlen`. With `payload_length()` explicitly tracked, all consumers construct `std::string_view(buf.data(), secret.payload_length())`, which works safely regardless of whether trailing null bytes exist.
- **STOP**: Confirmed accepted. Compatibility with V1 binary format is 100% preserved.

## Consequences
- Passwords and binary tokens containing `0x00` can be stored and retrieved with zero truncation.
- `strnlen()` is completely eliminated from the codebase.
- Compatibility with existing V1 vault files is preserved.
