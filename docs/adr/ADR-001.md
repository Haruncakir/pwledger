# ADR-001: Secure Serialization Buffer (`SecureBuffer`)

## Status
Accepted

## Date
2026-10-21

## Context
In `pwledger_core`, `VaultSerializer::serialize()`, `VaultSerializer::deserialize()`, `VaultCrypto::encrypt_vault()`, and `VaultCrypto::decrypt_vault()` currently use `std::vector<uint8_t>` to hold the decrypted vault payload.

Although `VaultIO.cc` calls `sodium_memzero()` after encryption, `std::vector<uint8_t>` introduces critical vulnerabilities:
1. **Reallocation Leaks**: As entries are appended during serialization, `std::vector` may grow its capacity by reallocating. The runtime CRT heap allocator leaves the previous chunk in heap memory without zeroing it.
2. **Page Swapping & Core Dumps**: Standard CRT heap allocations are pageable to the OS swapfile/pagefile and are captured in process core dumps.
3. **No Guard Pages**: Standard vectors lack hardware protection (`PAGE_NOACCESS` guard pages) before and after the buffer.
4. **Exception Leaks**: If an exception is thrown prior to `sodium_memzero()`, the vector's default deallocator releases plaintext secrets directly to the heap free-list without wiping.

## Decision
Introduce a dedicated, move-only, RAII-hardened container `pwledger::SecureBuffer` backed entirely by libsodium primitives:
- **Allocation & Memory State**: Backed by `sodium_malloc()`, locking pages into physical memory (`mlock` / `VirtualLock`), surrounding allocations with hardware guard pages (`PAGE_NOACCESS`), and disabling swappability.
- **Operational Memory State (RW Duration)**: `SecureBuffer` is an ephemeral work buffer used during active serialization, deserialization, encryption, and decryption operations. It remains in `PAGE_READWRITE` state for the duration of the operation to avoid tens of thousands of system calls (`mprotect`) during field-by-field serialization. Its lifecycle is strictly scoped to the active operation.
- **Safe Reallocation & Exact Reserve**: Capacity growth (`reserve()` or reallocation) allocates a new `sodium_malloc()` buffer, copies active bytes, wipes the old buffer with `sodium_memzero()`, and frees it via `sodium_free()`. No secret bytes ever remain in abandoned memory.
- **Deterministic Cleanup**: The destructor calls `sodium_memzero()` across the entire allocated capacity before calling `sodium_free()`.
- **Untrusted Sized Allocation (Tier 2)**: To prevent an attacker-controlled huge file from causing an unrecoverable `std::abort()` via `sodium_malloc()`, `SecureBuffer` enforces a maximum size check (`kMaxSecureBufferBytes = 64 * 1024 * 1024` / 64 MiB) and provides non-aborting allocation methods (`try_allocate()`) that throw typed `std::bad_alloc` or `std::runtime_error` instead of aborting. Fixed-size internal allocations (e.g. 32-byte keys) retain Tier 1 abort-on-failure behavior.
- **Zero-Allocation Views**: Access is provided strictly through `std::span<uint8_t>` and `std::span<const uint8_t>`, `data()`, and `size()`.

## Doubt-Driven Scrutiny
- **CLAIM**: `SecureBuffer` eliminates all secret leaks during vault serialization while maintaining equivalent performance and ergonomics.
- **EXTRACT**:
  ```cpp
  SecureBuffer plaintext = VaultSerializer::serialize(table);
  SecureBuffer ciphertext = VaultCrypto::encrypt_vault(password, plaintext);
  ```
- **DOUBT**: `sodium_malloc()` imposes an allocation overhead of at least two guard pages (typically 8 KB to 16 KB) and system calls (`mprotect`, `mlock`). If `SecureBuffer` reallocates frequently, will serialization become prohibitively slow?
- **RECONCILE**: Vault serialization happens only when explicitly saving to disk (CLI exit or user CRUD action), not in a high-frequency loop. Vault sizes for typical personal vaults (1,000 entries) are under 500 KB. Furthermore, `VaultSerializer` can pre-calculate the required serialized size (`reserve()`) before appending entries, resulting in exactly one initial `sodium_malloc()` call and zero reallocations.
- **STOP**: Confirmed accepted. Security guarantee completely outweighs sub-millisecond allocation overhead.

## Alternatives Considered
- **Custom `std::allocator` for `std::vector`**:
  *Pros*: Retains `std::vector` interface.
  *Cons*: C++ allocators cannot intercept `vector` reallocation to zero old memory before deallocation; `std::vector` move operations and internal growth algorithms can lead to subtle zeroing misses.
- **Keep `std::vector` and use `sodium_mlock`**:
  *Pros*: Minimal change.
  *Cons*: Does not prevent reallocation leaks or provide guard pages.

## Consequences
- All cryptographic and serialization operations in `pwledger_core` run entirely within page-locked, guard-page-protected memory.
- Plaintext vault serialization leaves zero residual secrets in the standard process heap.

## Secret Memory Scaling & Bound Limits (Amendment 6)

### Libsodium `sodium_malloc` Behavior & Failure Modes
According to official libsodium documentation ([doc.libsodium.org/memory_management](https://doc.libsodium.org/memory_management)):
1. `sodium_malloc(size)` allocates memory aligned to page boundaries, enclosing the region with `PAGE_NOACCESS` guard pages before and after. Each allocation consumes at least 3 pages (12 KB of virtual address space on 4 KB page architectures: 1 pre-guard page + data pages + 1 post-guard page).
2. `sodium_malloc()` attempts to lock pages via `mlock()` (POSIX) or `VirtualLock()` (Windows).
3. **If `mlock()` fails or `RLIMIT_MEMLOCK` is exceeded**: `sodium_malloc()` does **not** fail; it continues without locking the page into RAM, but canaries and hardware guard pages remain active.
4. **However, if virtual memory allocation (`mmap`) fails**: `sodium_malloc()` returns `NULL`, which causes `Secret::allocate()` to immediately invoke `std::abort()`.

> [!NOTE]
> **Kernel Failure Threshold Analysis**:
> In Linux kernels where `vm.max_map_count` is at the legacy default of `65,530`, each `sodium_malloc` consumes 3 VMAs (guard + page + guard). Each entry contains 2 `Secret` objects (`plaintext_secret` and `salt`), consuming 6 VMAs per entry. At `65,530 / 6 ≈ 10,921` entries, `mmap` calls fail with `ENOMEM`, causing `sodium_malloc` to return `NULL` and the original code to abort.
> On Ubuntu 24.04 (Noble), the kernel ships with `vm.max_map_count = 1,048,576`, enabling tests up to 50,000 entries (300,000 VMAs) without kernel exhaustion, but consuming 1.65 GB of physical RSS. Setting `kMaxEntries = 10,000` guarantees graceful operation on all standard Linux installations.

### Derived Safe Limits for Deserialization Bounds
To guarantee that no valid vault that the ORIGINAL code could open is ever made unreadable, we examine the original code's operational ceilings:
- `NativeMessaging.h` sets `kMaxMessageBytes = 1,048,576` (1 MiB), bounding any message passing between extension and host.
- `apps/cli/CommandLoop.cc` uses `std::getline()`, which has no arbitrary cap.
- `SecretEntry.security_policy.note` can legitimately hold large notes, recovery seeds, or multi-kilobyte keys.

We establish generous, per-field limits that accommodate all legitimate payloads:
- **`kMaxEntries = 10,000` (Graceful Limit)**:
  - Exceeding this limit throws a typed `VaultCorruptException("Vault entry count exceeds maximum supported limit (10000)")`. It does **not** crash or abort.
  - If `sodium_malloc()` returns `NULL` when allocating a secret during deserialization of an untrusted file, the loader catches the condition and throws `VaultCorruptException("Insufficient memory for vault entries")`.
  - This limit is driven by the Linux kernel default `vm.max_map_count` (65,530), ensuring portability across default Linux desktop installations (it is theoretically looser on Windows/macOS).
- **`kMaxTitleLen = 65,536` (64 KB)**: Extremely generous ceiling for entry titles and service URLs.
- **`kMaxUsernameLen = 65,536` (64 KB)**: Extremely generous ceiling for usernames or emails.
- **`kMaxNoteLen = 1,048,576` (1 MB)**: Accommodates large notes, PGP keyrings, and multi-page text blocks up to the 1 MiB native messaging limit.
- **`kMaxSecretLen = 1,048,576` (1 MB)**: Accommodates large binary certificates, private keys, and high-entropy secret payloads.
- **Residual Compatibility Risk**: In the implausible scenario that an original vault contained a single note or secret exceeding 1 MiB, it would exceed these limits; this is documented in README under "Known Limitations".
